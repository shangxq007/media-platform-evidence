## Sequencing design and limits

Subscribe before asynchronous initial getUser. The first trustworthy hydration establishes the baseline without a fake switch. Each native notification invalidates pending hydration/reads with a subscription-local revision; cleanup also deactivates the callback. Definitive invalidation/signout initiation clears baseline and retires synchronously, even when redirect fails. Loaded events use a current SDK getUser(false) read before accepting an identity update. The event payload never supplies identity: a fresh current-user read observes B even when an old A notification triggered it. If B was already established this preserves editing; if B was still pending it correctly retires A. A read from an older notification cannot affect the newer owner. This is subscription-local lifecycle bookkeeping, not a second authorization store. SDK source events are awaited promises; a changed UserLoaded may retire after the read, before its returned promise settles. Payloadless invalidations retire synchronously.

The SDK does NOT label events with source operation generations. If a stale SDK sign-in operation actually overwrites current storage and then emits UserLoaded, it is indistinguishable from a current sign-in; differing/unknown continuity must retire. Likewise payloadless unload/expiry/session signals cannot identify an old principal: they fail closed. No timestamp, token comparison or tombstone list can safely invent that distinction. SDK getUser also refreshes its timers; this bounded consumer does not redesign SDK authentication storage/operations. Silent renew failures alone are not definitive expiry and are not wired as logout. Real IdP sid stability, issuer/tenant semantics, remote logout notification and server session-bound access remain unverified; UXW1-002 and FB-GAP-001/002 must record these limitations. No browser or real authentication PASS is claimed.

Final review found and reproduced an additional interleave: B notification/read pending, then old A notification reads current B. Merely ignoring mismatched payloads lost B because A superseded the pending read. interleave-red.json captures the failure. The final callback treats UserLoaded as a read trigger and always observes the latest successful SDK read; it never uses the event payload as identity. This preserves established B and also detects B when still pending.
